# ADR-0002 · 시각은 순간(`timestamptz`)으로 저장하고, 노출·계산은 KST 로 고정한다

> 상태: 채택 · 날짜: 2026-08-28 · 출처: [PLAN-REQ-16](../plans/PLAN-REQ-16-time-handling-timestamptz.md)

## 맥락

19개 시각 컬럼이 전부 `timestamp`(오프셋 없음)다. **값 자체가 자기 타임존을 밝히지 못한다.**

그 결과 세 가지가 겹쳐 있었다.

- **같은 컬럼에 기준이 다른 값이 섞인다.** 앱은 `hibernate.jdbc.time_zone: UTC` 로 UTC 를 쓰고, DB `default now()` 는 세션 타임존으로 쓴다. 2026-07-30 에 실제로 목격했다 — 앱이 쓴 행 `14:39`, `now()` 로 심은 행 `23:38`. 앱끼리는 일관적이라 **버그로 드러나지 않고** SQL 로 데이터를 다룰 때만 나타난다
- **"이 값은 UTC 다"가 설정 한 줄에만 적혀 있다.** 그 줄을 모르는 사람이 데이터를 심으면 9시간 어긋난 행이 조용히 들어간다. 타입이 스스로 말해 주지 않으므로 규약을 사람이 기억해야 한다
- **달력 판정의 기준이 없다.** REQ-10 Phase 3 이후가 요구하는 "당일 시간만 허용"(급여) · "미래 날짜 불가"(다이어리) · 거식 스트릭 **일수** · 탈피 **주기**는 전부 자정 경계를 필요로 하는데, 어느 타임존의 자정인지 원본에도 코드에도 없다

즉 **저장 형식이 정보를 잃고 있고, 그 손실을 코드 밖의 암묵 규약이 메우고 있는** 상태였다. 사용자는 전원 국내이며 "날짜는 전부 KST"를 요구했다.

## 결정

시각 컬럼을 **`timestamptz`** 로 전환한다. 저장하는 것은 "벽시계 문자열"이 아니라 **순간(instant)** 이고, 타임존 해석은 저장이 아니라 **경계에서** 한다.

- **노출** — 응답은 KST 오프셋을 붙여 내보낸다(`2026-06-30T18:00:00+09:00`). 직렬화 계층 한 곳에서 변환한다
- **계산** — "오늘"·"당일"·"미래"·"일수"·"주기" 등 달력 판정은 전부 `Asia/Seoul` 자정 경계
- **`now` 획득** — `Clock` 을 주입한다. `LocalDateTime.now()` 직접 호출을 없앤다

`date` 컬럼(`entry_date`·`measured_at`·`shed_date`·`birthday`·`adoption_date`)은 타입을 바꾸지 않는다 — 날짜만 있는 값에는 타임존 개념이 없다. 다만 그 값과 "오늘"을 비교할 때 KST 달력을 쓴다.

## 기각한 안

- **KST 로 저장 (`timestamp` 유지)** — 변환이 아예 없어 SQL 로 본 값과 사용자가 본 값이 같아진다는 이점이 있다. 그러나 "JVM 기본 TZ 가 KST", "DB 세션 TZ 가 KST"라는 **암묵 전제** 위에 서고, 컨테이너에 `TZ` 를 안 넣거나 Supabase 세션 TZ(UTC)를 만나면 **에러 없이** 9시간 어긋난다. 이 프로젝트가 반복해 밟은 조용한 실패(`.env` 의 빈 값이 기본값을 무력화한 건, `db.schema` 를 한쪽만 배선한 건)와 같은 얼굴이다.
  **재검토 조건**: 없음. 암묵 TZ 의존을 되살릴 이유는 생기지 않는다.

- **UTC 저장 + `timestamp` 유지 (현행)** — 이행 비용이 0 이고, 틀리면 9시간 차이로 눈에 띈다는 점에서 KST 저장보다 낫다. 그러나 **값이 여전히 자기 타임존을 밝히지 못해** 규약을 사람이 기억해야 하고, DB `now()` 와 앱이 갈리는 07-30 함정이 그대로 남는다.
  **재검토 조건**: 데이터가 무중단 마이그레이션이 불가능할 규모로 커진 뒤에 이 결정을 되돌려야 할 상황. 배포 전인 지금이 전환 비용이 가장 싸다는 것이 채택의 절반이다.

- **계정별 타임존 (사용자 설정)** — 같은 대화에서 제안됐다가 철회됐다("그냥 KST로 고정가자"). `users.timezone` 컬럼 · `PATCH /users/me` 확장 · 요청 스코프로 TZ 를 나르는 framework 포트가 따라오는데, 사용자가 전원 국내인 현재로선 그 복잡도를 살 이유가 없다.
  **재검토 조건**: 해외 사용자 유입 또는 다중 타임존 요구. ⭐ **이때 재마이그레이션이 필요 없다** — `timestamptz` 는 이미 순간을 저장하므로 경계의 변환 대상만 KST 고정에서 사용자 값으로 바꾸면 된다. 이것이 이 안을 "기각"이 아니라 "연기"로 만들 수 있는 이유이고, 채택의 나머지 절반이다.

- **응답을 `Z` 로 내보내기** — 원본(Notion `API I/F`) 예시 표기와 같아진다. 그러나 저장 형식이 UTC 라는 **내부 사정을 API 계약에 노출**하고, 클라이언트가 KST 변환을 각자 구현하게 되어 목록 소비자마다 갈린다. 같은 순간의 다른 표기이므로 원본 예시는 역반영 대상이지 계약 위반이 아니다.
  **재검토 조건**: 클라이언트가 여러 타임존에 걸치게 될 때 — 위 "계정별 타임존"과 같은 트리거다.

## 결과

감수하기로 한 비용:

- **클라이언트 계약이 바뀐다.** `created_at` 표기가 전 도메인(auth · user · pet · weight · activity)에서 달라진다. 앱 구현 전이라 지금이 가장 싸지만, 공짜는 아니다
- **엔티티 6필드와 DTO 6파일의 타입이 바뀐다.** `LocalDateTime` 을 그대로 둘 수 없다 — 어떤 타입으로 갈지는 프로브로 정한다(PLAN-REQ-16 미결 ①)
- **`V3` 를 이 작업이 가져간다.** REQ-10 Phase 3 의 `feeding_logs.food_size` 는 `V4` 로 밀린다
- **REQ-10 Phase 3 이 이 작업 뒤로 밀린다.** 달력 기준 없이 "당일"·스트릭 일수를 구현할 수 없기 때문이다
- **`hibernate.jdbc.time_zone: UTC` 의 의미가 달라진다.** `timestamp` 시절의 근거로 남겨 두면 안 된다

얻는 것:

- **07-30 함정이 사라진다.** `timestamptz` 컬럼에서 `now()` 는 세션 타임존과 무관하게 올바른 순간을 반환한다. 다만 그때 세운 픽스처 규칙(`now() at time zone 'UTC'`)도 **함께 폐기해야 한다** — 남겨 두면 이번엔 반대 방향으로 9시간 어긋난다
- **타입이 규약을 대신 기억한다.** "이 값이 어느 타임존인가"를 사람이 알 필요가 없어진다
