# ADR-0001 · 파생 상태는 단일 출처에서만 저장한다 — `condition_tag` 는 4종

> 상태: 채택 · 날짜: 2026-08-27 · 출처: [PLAN-REQ-10-record-domains](../plans/PLAN-REQ-10-record-domains.md) (D1)

## 맥락

다이어리 `condition_tag` 의 허용값이 원본끼리 어긋나 있었다.

- Notion `API I/F` → 다이어리 작성: **4종** `정상 | 활발 | 거꾸리 | 구토` — 그리고 이유가 적혀 있다: *"거식·탈피는 급여·탈피 기록에서 파생, 단일 출처"*
- Notion 테이블 정의서 · 「소스 구조」 §8 · ERD · `docs/specs/api-list.md` §4: **7종** (+ `거식` · `탈피도와줌` · `탈피완료`), 그리고 `shed_records.is_assisted = true ↔ condition_tag '탈피도와줌'` 연계 규칙

같은 사실(거식 중이다 · 탈피했다)이 두 테이블에 저장되면 **어느 쪽이 진실인지 정할 수 없다.** feeding 에 `is_refused` 가 찍혔는데 diary 에 `거식` 태그가 없으면 거식인가 아닌가. 이 프로젝트의 차별점인 게코 파생 로직(거식 스트릭 · 탈피 예측)은 전부 **원본 기록에서 계산**하는 구조라(「소스 구조」 §1-4 "파생 상태는 저장하지 않고 계산한다"), 다이어리에 파생값을 따로 저장하는 것은 그 원칙과 정면으로 부딪힌다.

## 결정

**파생될 수 있는 상태는 그것을 만드는 원본 기록에만 저장하고, 다른 테이블에 복제하지 않는다.** 구체적으로 `diary_entries.condition_tag` 는 **다이어리 자체의 관찰**만 담는 4종(`정상 · 활발 · 거꾸리 · 구토`)이고, 거식은 `feeding_logs.is_refused`, 탈피는 `shed_records` 에서만 나온다. 타임라인·캘린더가 "그날 거식/탈피" 를 보여 줘야 하면 **조회 시 원본을 읽어 이벤트로 파생**한다(`API I/F` 통합 타임라인 행이 이미 그렇게 적고 있다 — "거식·탈피 상태는 feeding·shed 원본에서 파생되어 이벤트로 표기").

이 결정은 `condition_tag` 하나에 그치지 않는다. 앞으로 "기록 A 의 상태를 기록 B 에도 태그로 남기자"는 제안이 오면 이 ADR 이 기준이다.

## 기각한 안

- **7종 유지 (테이블 정의서 쪽을 따른다)** — 문서 세 곳이 이미 그렇게 적혀 있어 손이 덜 간다. 그러나 `is_assisted ↔ '탈피도와줌'` 같은 **연계 규칙을 코드로 지켜야** 하고, 한쪽만 갱신되는 순간 조용히 갈라진다. 사용자가 다이어리에 `거식` 을 직접 찍을 수 있게 되면 feeding 기록과 무관한 "거식"이 생긴다. / **재검토 조건**: 다이어리가 feeding·shed 와 **독립적으로** 거식·탈피를 기록해야 하는 요구가 기획에서 나올 때 — 예를 들어 급여 기록 없이 "오늘 거식이었다"만 남기고 싶다는 사용자 요구가 확인될 때. 그때는 4종에 값을 더하는 게 아니라 **feeding 에 "기록 없는 거식"을 표현하는 방법**을 먼저 검토한다
- **4종 + 서버가 자동으로 거식·탈피 태그를 diary 에 써 준다** — 단일 출처처럼 보이지만 결국 두 테이블에 같은 사실이 있고, feeding 을 지우면 diary 태그도 지워야 하는 연쇄가 생긴다. / **재검토 조건**: 없음 — 복제의 다른 모양이다

## 결과

- **역반영 3곳** — Notion 테이블 정의서 `diary_entries` · 「소스 구조」 §8 "condition_tag 7종 확정" · ERD. 레포는 `docs/specs/api-list.md` §4 · `db-schema.md`. `V1__init.sql` 주석(4종)은 **우연히 맞게 되어** 고칠 일이 없다(적용된 마이그레이션은 주석도 못 고친다)
- `is_assisted ↔ '탈피도와줌'` 연계 규칙은 **폐기 또는 timeline 이벤트로 이관** — PLAN-REQ-10 미결
- 타임라인(REQ-12)은 diary 만 읽어서는 "거식/탈피"를 표시할 수 없다 — 5개 테이블 union 이 어차피 전제였으므로 추가 비용은 없다
- `ConditionTag` enum 은 4개. "왜 7개가 아닌가"는 코드에 남지 않으므로 enum javadoc 에서 이 ADR 을 가리킨다
