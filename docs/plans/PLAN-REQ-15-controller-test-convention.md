# PLAN-REQ-15 · 컨트롤러 테스트 관례 도입 (`@WebMvcTest`)

> 출처: 2026-08-07 세션 (REQ-08 Phase 1~3 · `/testrun` 지적) · 작성: 2026-08-07 · 상태: 🟡 진행 (Phase 1~2 완료 · **Phase 3 은 작성 완료·사람 판정 대기**)

## 배경

**REQ-08 자동 테스트 24건이 전부 초록불인데, HTTP 왕복이 있어야만 검증되는 지점 3건은 "사람이 한 번 본 것"뿐이다.** 셋 다 회귀하면 조용하다.

| 지점 | 테스트가 덮는 곳 | **안 덮는 곳** |
|---|---|---|
| `GET /users/me` 전역 snake_case | `REQ-08-01` — record 컴포넌트 이름(camelCase) | 직렬화된 JSON 키. `JacksonConfig`가 사라져도 초록불 |
| 101자 닉네임 → 400 | `REQ-08-06` — Bean Validation 위반 생성 | `MethodArgumentNotValidException` → `INVALID_INPUT` 매핑 |
| 탈퇴 토큰 → 401 | `REQ-08-16` — 인증 미설정 + 체인 계속 | `authenticationEntryPoint`가 내는 401과 본문 형태 |

셋 다 2026-08-07 로컬 왕복에서 눈으로 확인했다(5필드 snake_case · 400 `INVALID_INPUT` · 401 `UNAUTHORIZED`). **하지만 한 번 봤다는 것과 고정됐다는 것은 다르다.**

> **그 차이가 실제로 사고를 냈다.** 같은 날 카카오 로그인이 **한 번도 동작한 적 없다**는 사실이 드러났는데, 그때 REQ-07 검증 계약 23건은 전부 초록불이었다. 단위 테스트가 `KakaoOAuthClient`를 목으로 대체해 그 경로를 한 번도 타지 않았기 때문이다(`bf41915`). **"단위 테스트 통과"와 "동작함" 사이의 거리**가 이 REQ의 존재 이유다.

그리고 이건 REQ-08만의 문제가 아니다. **REQ-09(pet)~REQ-12(timeline)의 컨트롤러가 전부 같은 공백을 갖게 된다.** 나중에 정하면 네 도메인을 소급해야 한다.

## 범위

**포함**

- `@WebMvcTest` 기반 컨트롤러 테스트 **관례 확정** — 무엇을 목으로 두고 무엇을 실물로 태울지, 시큐리티를 어디까지 태울지
- 위 표의 **공백 3건을 닫는 케이스** 작성 (REQ-08 소급) + **`AuthController` 적용**(D8) — `POST /auth/kakao`(공개 경로)·`DELETE /auth/logout`(204)
- AGENTS.md에 관례 기록 — 다음 도메인이 따라갈 대상

**제외**

- **`@SpringBootTest` + 실 DB 통합 테스트** — 2026-08-07 REQ-08 Phase 2 착수 시 `REQ-08-11` 자동화 방안으로 검토했다가 **"구현 후 사람이 수동 검증"으로 결정**된 이력이 있다. 이번에도 되살리지 않는다. 목적이 다르다 — 이 REQ는 **웹 계층 계약**(직렬화·상태코드·에러 본문)을 고정하는 것이지 DB 왕복을 자동화하는 게 아니다
- **Testcontainers** — PLAN-REQ-07에서 기각된 이력(로테이션·재사용 감지는 저장소 호출만 관찰하면 되는 순수 흐름)
- **`REQ-08-11`(탈퇴 → 재로그인 새 `users.id`)의 자동화** — 계획서가 "목으로는 D1이 검증되지 않는다"고 못 박은 케이스다. `UNIQUE (provider, provider_user_id)`와 실제 조회 결과가 만드는 현상이라 **웹 계층 테스트로는 성립하지 않는다.** 수동으로 남긴다
- **기존 단위 테스트 삭제** — **병행하기로 확정(D6).** `REQ-08-01`·`06`·`16` 은 그대로 둔다
- **REQ-09 이후 도메인의 컨트롤러 테스트 작성** — 이 REQ는 관례를 정하고 REQ-08에 시범 적용까지다. 이후 도메인은 각자의 REQ에서 관례를 따른다

## 프로브 결과 (2026-08-07 실측)

미결 ②를 문서가 아니라 **실제로 띄워서** 닫았다. 네 가지가 나왔고, 셋은 모르면 반드시 밟는다.

| # | 관찰 | 함의 |
|---|---|---|
| 1 | **`JwtAuthenticationFilter` 가 슬라이스에 자동 포함된다** (`Filter` 빈이라서) | `JwtTokenProvider` 를 채우지 않으면 **컨텍스트가 아예 안 뜬다.** `@AutoConfigureMockMvc(addFilters = false)` 로도 **빈 생성은 막히지 않는다** |
| 2 | **`SecurityConfig` 는 `@Import` 해야 한다** | 없으면 Spring Boot **기본 시큐리티**가 401 을 내는데 **본문이 비어 있다.** 우리 계약은 `{"data":null,"error":{"code":"UNAUTHORIZED",…}}` 다 |
| 3 | ⭐ **`JacksonConfig` 도 `@Import` 해야 한다** | 없으면 응답이 **`profileImageUrl`(camelCase)** 로 나간다. 실제 앱은 `profile_image_url` 이다 |
| 4 | ⭐ **`UserStatusChecker` 를 따로 `@MockBean` 하면 안 된다** | `UserService` 가 그 인터페이스를 구현하므로(D2) 두 목이 충돌해 **`UserService` 정의가 사라지고** `userController` 생성이 실패한다. 에러는 "`UserService` 없음"이라 **원인이 안 보인다.** `@MockBean UserService` 하나가 둘 다 만족시킨다 |

> ⭐ **3번이 이 REQ 의 존재 이유를 그대로 재현한다.** `@Import(JacksonConfig)` 없이 짰다면 테스트는 `profileImageUrl` 을 단언하고 **통과했을 것**이다 — 실제 계약과 반대인 값을 초록불로 굳히는 셈이고, 심하면 누군가 그걸 보고 **DTO 를 "고쳐" 운영을 깬다.** 사용자 정의 `@Configuration` 이 슬라이스에서 조용히 빠지는 것이 원인이다.

**확정 설정으로 공백 3건이 전부 닫히는 것까지 확인했다.**

| 대상 | 프로브 결과 |
|---|---|
| `GET /users/me` | `200` · `profile_image_url`·`created_at` **snake_case 확인** · `updated_at` 없음 |
| `PATCH` 101자 | `400` `{"code":"INVALID_INPUT","message":"nickname: size must be between 0 and 100"}` |
| `DELETE` | `204` · 본문 0바이트 |

- 인증은 `spring-security-test` 의 `SecurityMockMvcRequestPostProcessors.authentication(...)` 에 `AuthPrincipal` 을 실은 토큰을 넘겨 만든다. `@WithMockUser` 는 `AuthPrincipal` 을 만들지 못해 쓸 수 없다
- ⚠️ **검증 메시지가 로케일을 탄다.** 프로브에서는 영어(`size must be between 0 and 100`)로 나왔는데 실제 앱 왕복에서는 한글(`크기가 0에서 100 사이여야 합니다`)이었다. **메시지 문자열을 단언하지 말고 `code` 를 단언할 것**

**`REQ-15-07` 은 "401 이 아니다"만 단언한다.** 빈 body 로 호출하면 `code` 의 `@NotBlank` 때문에 400 이 나오는데, **이 케이스가 재는 것은 상태코드가 아니라 "이 경로가 시큐리티에 막히지 않는다"** 이다. 400 을 정확히 단언하면 케이스가 재는 것이 "공개 경로임"인지 "검증 동작"인지 흐려진다.

**`@Import` 누락은 별도 케이스를 두지 않는다.** 프로브 결과 3번(`JacksonConfig` 가 빠지면 camelCase)은 **`REQ-15-01` 이 그대로 잡는다.** 설정을 검증하는 케이스를 따로 두면 테스트를 테스트하는 꼴이다.

**Phase 3(관례 기록)에는 케이스가 없다.** 완료 기준이 "다음 담당자가 이 문서만 보고 쓸 수 있는가"라 **자동 검증이 성립하지 않는다.** 억지로 만들면 그게 가짜 테스트다 — 사람이 읽고 판정한다.

## 제약·함정

- **프로브 없이는 이 REQ가 무의미하다** (CLAUDE.md) — 목적 자체가 "초록불인데 검증이 안 되던 것"을 닫는 것이다. 새 테스트가 **실제로 그 결함을 잡는지** 심어서 확인하지 않으면 공백을 공백으로 덮는 셈이다. 2026-08-07 `REQ-07-24`가 그 예다 — **설정된 ObjectMapper로 검증했다면 버그가 있어도 초록불이었다**
- **`@WebMvcTest`는 슬라이스라 전체 컨텍스트가 아니다.** 여기서 통과했다고 실제 기동이 보장되지 않는다 — Bean 배선·Flyway·DB는 여전히 밖이다. **"@WebMvcTest 통과 = 동작함"으로 넓혀 읽지 말 것.** 이 REQ가 고치려는 오해와 같은 종류다
- **테스트명에 케이스 ID를 박는다** (CLAUDE.md) — `@DisplayName` + 메서드명 양쪽. 어긋나면 에러가 아니라 **"0건 통과"**로 나타난다
- **Gradle `--tests`는 메서드명으로 필터한다.** `@DisplayName`에만 ID를 두면 필터가 성립하지 않는다. 또 `--tests`는 `[45]` 같은 문자클래스를 지원하지 않는다(2026-08-07 실측)
- **ArchUnit은 프로덕션 코드만 본다** (2026-08-04, `DoNotIncludeTests`) — 테스트를 미러 패키지에 둬도 `DTO_NAMING`·`CONTROLLER_NAMING`에 걸리지 않는다. 되돌리지 말 것
- **의존성을 추가하지 않는다** (D3) — 필요해 보이면 그건 관례가 잘못 잡힌 신호일 수 있다. 추가 전에 제안·승인(AGENTS §7)
